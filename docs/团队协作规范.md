# 团队协作规范

> 适用于 Aimback 项目一周冲刺（v0 网页版）。规则以「能记住、能执行」为准，凡是不写会踩坑的才写进来。
>
> 人员代号沿用《技术路径大纲01》第 5 节：A 叶建新、B 李子骞、C 赵悦、D 车艾佳、E 孙文博、F 涂美灵、G 吴娴越（非开发）。

## 0. 三条铁律

其余内容都是解释和细节，只记住这三条也能不出大事：

1. **只在自己的分支上写代码，永远不直接推 `main`。**
2. **每天开工先把 `main` 拉进自己分支，收工前把自己分支推到远程。**
3. **改到别人负责的文件之前，先在群里说一声。**

## 2. 分支规则

### 2.1 分支模型

每人一条固定的个人分支，从头用到尾：

| 分支 | 归属 |
| --- | --- |
| `main` | 受保护，只能通过 PR 合入 |
| `dev-a` | A |
| `dev-b` | B |
| `dev-c` | C |
| `dev-d` | D |
| `dev-e` | E |
| `dev-f` | F |

不要在别人的分支上提交，也不要随手建一堆临时分支。

### 2.2 `main` 分支保护

仓库设置里对 `main` 开启：

- 禁止直接推送，必须通过 Pull Request
- 禁止强制推送（force push）
- 禁止删除分支
- **不要求**他人审查批准，PR 可以自己合并

一周冲刺不设正式评审，保护规则只用来防误操作，不用来卡进度。

### 2.3 什么时候必须合并到 `main`

不强制每天合，但下面几种情况必须合：

1. 一个功能真正做完、本地能跑通时，当天就合。
2. **第 3 天收工前所有人必须合一次**。第 4 天开始联调，`main` 上必须有全组的代码。
3. 第 4 天进入联调后，改动尽快合，不要攒。
4. 别人明确在等你的代码时（例如 B、C、E 等 A 的 Django 骨架），立刻合。

**没做完的功能不要合。** 个人分支上允许有半成品，`main` 上不允许。

### 2.4 每天必须做的两件事

这两件和「合并到 `main`」是两回事，都不影响别人，但每天都要做：

**开工时：把 `main` 最新代码合进自己分支。**
不做这一步，你的分支会和别人越差越远，最后一次合并会非常痛苦。

**收工前：把自己分支推到远程（push）。**
理由有三个：电脑坏了代码还在；别人能看到你的进度；站会时可以直接指着代码说。推个人分支不会影响任何人，尽管推。

### 2.5 第 1 天的特殊顺序

第 1 天有两条卡人的关键路径，请按顺序来，不要并行开写：

1. **A 先把 Django 工程骨架合进 `main`**，B、C、E 才能拉下来建自己的 app。
2. **D 独立把 Vite + Vue 工程骨架合进 `main`**，同时提交 `frontend/web/README.md`，F 才能开始跑环境、写页面。

骨架进 `main` 之前，等待的人先做不依赖代码的事：B 推进短信联调调研，C 和 A 对齐认领字段，E 打通向量化 API 的最小 demo，F 出视觉稿。

D 的 setup 文档要写到「照着敲就能跑」的程度，至少包含：node 版本要求与安装链接、`npm install` 与启动命令、每一步的预期输出、自己踩到的报错及解决办法。这是线上协作的替代方案——写清一次，省掉 F 反复来回问。F 跑通后发现文档漏了步骤，直接补进去再提交，不用等 D。

## 3. 提交信息规范

格式：

```text
类型-代号(范围): 中文说明
```

类型只用这五个：

| 类型 | 用于 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 只改文档 |
| `refactor` | 重构，不改行为 |
| `chore` | 依赖、配置、构建、杂项 |

代号用小写 a 到 f，写提交人的代号，和个人分支 `dev-a` 风格一致；范围写改的功能模块，中文英文都行，保持自己前后一致：

```text
feat-a(帖子接口): 实现帖子列表的分类与地点硬过滤
feat-d(发布页): 完成表单校验与图片上传交互
fix-b(登录): 修复验证码倒计时刷新后重置的问题
docs-a(接口契约): 补充认领状态枚举
chore-b(部署): 添加 Nginx 反向代理配置
```

要求：

- 代号必填，写实际动手提交的人。结对完成时写主导人的代号；帮别人提交时写代码作者并在说明里补一句。
- 一句话说清「改了什么」，不写「更新」「改了下」「提交一下」这类看不出内容的话。
- 一次提交只做一件事。写了半天攒成一个巨型提交，出问题时无法回退。
- 提交频率不用省，本地随时提交，一天十几次都正常。

## 4. 合并到 `main` 的流程

1. 确认自己分支上的功能完整、本地能跑起来。
2. 先把 `main` 合进自己分支，在**自己分支上**解决完所有冲突。
3. 把自己分支推到远程。
4. 在 GitHub 上开 Pull Request：`dev-x` → `main`，标题写清这次合入的功能。
5. 页面显示 `Able to merge`（绿色）后，自己点 Merge。
6. **合并后不要删除个人分支**，后面还要继续用。

第 2 步很重要：冲突要在自己分支上解决，不要留到 PR 页面上处理。自己分支上改坏了还能重来，`main` 上改坏了会影响全组。

## 5. 冲突处理与求助

### 5.1 一般原则

- 冲突是正常的，不是谁犯错了，**不要偷偷自己乱改**。
- **绝对不要为了消除冲突直接删掉别人的代码。** 分不清哪段该留就去问原作者，这是最常见也最难查的事故。
- 冲突涉及别人的文件时，找那个文件的负责人一起看，两分钟能解决的事不要自己猜半小时。

### 5.2 Django 迁移文件冲突

后端四个人在同一个 Django 工程里，`makemigrations` 会各自生成编号相近的迁移文件，是本项目最容易出冲突的地方。约定：

- 只对**自己的 app** 执行 `makemigrations`，不要执行不带 app 名的全局 `makemigrations`。
- 迁移文件生成后不要手动改编号。
- 出现迁移冲突时找 A 处理，A 是数据模型负责人。
- 不要删除已经合进 `main` 的迁移文件，即使它看起来没用。

### 5.3 前端锁文件冲突

`package-lock.json` 冲突时不要手工合并，删掉它重新 `npm install` 生成，再提交。

### 5.4 卡住时怎么办

- **卡住超过半天，必须在群里说**，由 A 或 E 协调支援。不要独自消化到影响联调。
- **环境、脚手架、依赖安装这类问题例外：卡住 30 分钟就说。** 这类坑对踩过的人只值几分钟，对第一次装的人可能耗掉半天，而且除 B、E 外全员线上协作，求助本身有延迟，攒着问只会更慢。
- Git 操作卡住导致不敢提交，随时找会 Git 的人，这类问题通常五分钟能解决。
- 提问时带上：你想做什么、执行了什么、报错原文截图。只说「我这报错了」会来回问很多轮。

## 6. 接口契约变更流程

《接口契约.md》第 1 天冻结。冻结的是字段名、路径、请求与响应结构、枚举值和硬过滤规则。

前端从第 1 天起就基于 mock 数据开工，不等后端实现。所以**字段名一改，前端就白写**。变更按下面走：

1. 想改字段名、路径或返回结构的人，**先在群里说，不要直接改代码**。
2. 由 A 判断是否必要，确认后**由 A 修改《接口契约.md》并合进 `main`**。
3. A 在群里同步一次，明确说清「哪个接口、哪个字段、改成什么」。
4. 前端收到通知后再改，不要自己猜。

实现细节（内部函数、查询写法、性能优化）不算契约变更，自己改就行。

认领相关字段由 C 与 A 对齐后，仍由 A 落笔写进文档，避免两个人同时改同一份文件。

## 7. 密钥与禁止入库的文件

**云 API 密钥、数据库密码、短信服务凭证一律不进仓库。** 仓库是 Public，任何人都能看到，密钥一旦提交就等于公开泄露。

### 7.1 禁止提交的内容

- `.env` 及任何含真实密钥的配置文件
- 阿里云短信、腾讯云 COS 的 AccessKey / SecretKey
- Django `SECRET_KEY` 的生产值
- 数据库连接串中的真实密码
- 微信小程序 AppSecret
- 用户上传的真实图片、导出的数据库文件
- 含真实姓名、手机号、身份证号的测试数据

### 7.2 正确做法

- 密钥通过环境变量注入，代码里读环境变量。
- 提交一份 `.env.example`，只写变量名和示例值，不写真值。
- 需要给别人真实密钥时走私聊或群文件，不走仓库。
- 仓库根目录的 `.gitignore` 已配置好，不要随意删减其中的规则。

### 7.3 万一提交了密钥

1. **立刻在群里说**，不要指望没人发现。
2. **马上去云控制台把该密钥作废并重新生成**。这一步最重要——已经推上 GitHub 的东西，即使删掉提交，也要按已泄露处理。
3. 再由 B 或 A 处理仓库历史。

| 时间 | 事项 |

| 开工 | 把 `main` 合进自己分支 |
| 白天 | 随时本地提交，一次一件事 |
| 收工前 15 分钟 | 全员站会，对齐进度与接口变化 |

站会每人说三句：昨天做完什么、今天做什么、被什么卡住。有接口变化的当场说。

- 任务不用录进 GitHub Issues 或看板，沿用《技术路径大纲01》的分工表加站会口头对齐。
- 第 4 天起联调中发现的 bug，在群里指名给具体某人，说清「哪个页面、什么操作、期望什么、实际什么」。

## 9. Git 操作速查

客户端不作统一要求，GitHub Desktop、命令行、编辑器内置面板都行。以下两套等价。

### 9.1 GitHub Desktop

**首次配置（每人一次）**

1. 登录 GitHub 账号：`File → Options → Accounts`。
2. 克隆仓库：`File → Clone repository`，选 `TrisSun/Aimback`，指定本地路径。
3. 建自己的分支：`Current Branch → New Branch`，名字填 `dev-x`（x 为自己的代号），基于 `main` 创建。
4. 点 `Publish branch` 把分支推到远程。

**每天开工**

1. 顶部 `Fetch origin`。
2. 切到 `main`：`Current Branch → main`，点 `Pull origin`。
3. 切回自己分支 `dev-x`。
4. `Branch → Merge into current branch`，选 `main`，确认合并。

**日常提交**

1. 左侧 `Changes` 勾选要提交的文件。
2. 左下角 Summary 填提交信息，格式见第 3 节。
3. 点 `Commit to dev-x`。
4. 顶部 `Push origin`。

**合并到 main**

1. 先做完上面「每天开工」的四步，把 `main` 合进自己分支并解决冲突。
2. `Push origin`。
3. `Branch → Create Pull Request`，浏览器会打开 PR 页面。
4. 填标题，`Create pull request`，确认绿色的 `Able to merge` 后点 `Merge pull request`。
5. **不要点 `Delete branch`。**

**解决冲突**

Desktop 会列出冲突文件，点 `Open in editor`，在编辑器里处理 `<<<<<<<` / `=======` / `>>>>>>>` 三段标记：上半段是你的，下半段是别人的。留下正确的内容、删掉标记行，保存后回 Desktop 点 `Continue merge`。**分不清就去问对方，别猜。**

### 9.2 命令行

```bash
# 首次：克隆并建自己的分支
git clone https://github.com/TrisSun/Aimback.git
cd Aimback
git checkout -b dev-x
git push -u origin dev-x

# 每天开工：把 main 合进自己分支
git checkout main
git pull
git checkout dev-x
git merge main

# 日常提交
git add .
git commit -m "feat(发布页): 完成图片上传交互"
git push

# 准备合并到 main：先在自己分支解决冲突，再去 GitHub 开 PR
git checkout main
git pull
git checkout dev-x
git merge main
# 有冲突就改文件，然后：
git add .
git commit
git push
```

**禁止使用的命令**（除非有人在旁边指导）：

| 命令 | 原因 |
| --- | --- |
| `git push -f` / `git push --force` | 会覆盖远程历史，可能抹掉别人的提交 |
| `git reset --hard` | 会丢弃本地未提交的改动，不可恢复 |
| `git rebase` | 冲突处理比 merge 复杂，一周冲刺不需要漂亮的历史 |
| `git checkout .` / `git restore .` | 会一次性丢弃所有本地改动 |

想撤销改动又不确定后果时，先问，别试。
